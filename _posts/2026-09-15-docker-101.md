Clone a fresh repo, follow the README, and watch it fail anyway. Your Node version is two majors behind, a system library is missing, and the Postgres setup that runs on your teammate's machine refuses to start on yours. "Well, it works on my machine" is the classic punchline because every team has lived it. Docker's pitch answers exactly this: package the application together with everything it needs to run, and that package behaves the same on any machine that hosts it.

The usual mental model is that a container is a small virtual machine. That idea holds up until the first real question, and then it collapses, because a container is a Linux process that the kernel has convinced it owns an entire computer. Docker builds that convincing illusion. Even the name carries the idea: a shipping container is useful because the crane, the ship, and the truck all handle the same standard box regardless of the cargo inside.

## Suburbia vs. the Apartment

A virtual machine is a single-family house. Every house gets its own foundation, plumbing, and electrical panel, and stands alone on its own lot. Fully isolated, comfortable, and expensive, because every house duplicates all of that infrastructure. On a computer, the hypervisor (VMware, VirtualBox, KVM) is the developer building houses on shared land: every VM carries a full guest operating system, with its own kernel and its own boot sequence, and gigabytes of disk and RAM are allocated before the application even starts.

A container is an apartment in a shared building. Every unit leans on the same foundation and central plumbing, which here is the host kernel, and each unit still has a locked door, private rooms, and its own meter: a sealed user space with its own libraries and config. Isolation without duplication.

> **The key difference:** a hypervisor virtualizes hardware, and each guest boots a whole operating system on top of it. The Docker engine is ordinary software running on the host, and everything labeled container underneath it is a plain process.

## An Image Is a Blueprint, a Container Is a Running Copy

These two words get swapped constantly, so they are worth pinning down early. An **image** is the frozen artifact: a packaged filesystem plus the command to run when it starts. You build images from a Dockerfile or pull them ready-made from a registry like Docker Hub, and an image just sits there until something runs it.

A **container** is what you get when Docker runs that artifact: a live process with a writable copy of the image's filesystem underneath it. One image can run as many containers, the same way one floor plan fills an entire apartment building.

Day to day, the workflow looks like this:

```bash
docker pull node:20          # fetch an image from a registry
docker run -d -p 8080:80 --name web nginx
docker ps                    # what is running right now
docker exec -it web bash     # step inside the running container
docker rm -f web             # throw it away and start fresh
```

That `-p 8080:80` flag previews the networking story: the container sits on a private network, and the mechanism behind it arrives later, once namespaces enter the picture.

## Why Do Containers Start in Milliseconds?

Three properties do the work:

1. **A shared kernel.** The kernel is already running when you start a container, so startup means launching a process, and processes take milliseconds. A VM instead has to POST virtual hardware and boot a whole guest OS into RAM before the app gets a single cycle.
2. **A layered filesystem.** An image is a stack of read-only layers (OverlayFS in most setups), and layers are shared. Run a hundred containers from the same image and its layers exist once on disk, with each container adding only a thin writable layer on top. A 900MB image stays 900MB however many containers run from it.
3. **Native execution.** The process runs directly on the host CPU. A VM pays a virtualization tax on every cycle of work, while a container runs at native speed.

## The Illusion of a Whole Machine

So a container is just a process on your host. How does Docker convince that process it's running on a computer of its own? Two kernel features, one deciding what the process can see, the other deciding what it can use.

**Namespaces decide what it can see.** Docker launches the process with a set of fresh namespaces, and inside them:

- **PID**: its own process tree, where the application is PID 1, the first process that ever existed as far as it can tell.
- **NET**: its own network stack, with interfaces, routing table, and IP address.
- **MNT**: its own mount points, including its own root filesystem.
- **UTS**: its own hostname.
- **IPC / USER**: its own inter-process memory queues, and its own user and group ID mapping.

One honest caveat on that last one: Docker keeps ID remapping off by default, so root inside a container is still root on the host. That is the reason production images run the application as a non-root user, and the fix is a single line in the Dockerfile: `USER node` drops the process to the unprivileged user the base image already ships.

**Cgroups decide what it can use.** A cgroup is a kernel-enforced budget: this process may have 512MB of RAM and one CPU core, full stop. It can see a whole machine and is only ever allowed a slice of one.

The mental model that makes this stick is an office cubicle. The walls are namespaces: from your chair you see your desk, your monitor, and your files, while the rest of the floor stays out of view. The meter is the cgroup: you can flip every breaker in your cubicle, and building management still caps what you draw.

Pull the thread and the machinery turns out to be refreshingly boring. `docker run` parses flags in the client and hands the request to the daemon, `dockerd`. The daemon stacks the image layers and delegates to `containerd` and `runc`, and runc asks the kernel to clone the process with the right namespace and cgroup flags. The process is born inside its cubicle with the entrypoint running as PID 1. When you published that port earlier with `-p 8080:80`, this same machinery programmed the host's firewall to forward traffic into the container's NET namespace.

## Where Does the Data Go When a Container Dies?

Sooner or later an engineer runs a database in a container and feels the obvious worry: the filesystem is ephemeral, so what happens to the records when the container crashes or gets deleted?

For the writable layer, the honest answer is that they're gone. Writes land in that thin top layer via copy-on-write, and `docker rm` deletes it. That layer is scratch space by design. Anything that matters has to live outside it:

- **Named volumes** are Docker-managed storage under `/var/lib/docker/volumes`. Postgres writes to its data directory, the volume backs it, and the data outlives any container that used it. The right default for stateful services.
- **Bind mounts** map an exact host path into the container (`./src:/app`). Changes are visible instantly in both directions, which is what makes live-reloading local development work.
- **tmpfs mounts** live in memory only and vanish on restart, which suits secrets and other data that should leave no trace on disk.

## The Same Stack on Every Laptop

The first everyday payoff is environment parity. One Dockerfile pins the runtime, the system packages, and the database version, so everybody on the team runs the same Node and the same Postgres straight from the repo. `docker compose up` and the stack runs; `docker compose down` stops every container while the volumes hold the data for next time.

The second is wiring services together. A compose file declares the pieces, say an API, Postgres, and Redis, and Docker puts them on an isolated bridge network with built-in DNS. The API reaches its database at `postgres://db:5432` by service name alone:

```yaml
services:
  api:
    build: .
    ports:
      - "3000:3000"
    depends_on:
      - db
      - cache
  db:
    image: postgres:17
    volumes:
      - pgdata:/var/lib/postgresql/data
  cache:
    image: redis:7
volumes:
  pgdata:
```

Three services, one private network, one command. And note where `pgdata` sits: the database's durability lives in the volume, so the container itself becomes replaceable.

## Layers, Caching, and Smaller Images

Every instruction in a Dockerfile becomes a layer, and the build cache works strictly top-down: the first instruction whose inputs changed invalidates its layer and everything below it. Order is therefore a performance decision:

```dockerfile
# SLOW: any source edit reinstalls every dependency
FROM node:20
COPY . .
RUN npm install

# FAST: dependencies stay cached until the manifests change
FROM node:20
COPY package.json package-lock.json ./
RUN npm install
COPY . .
```

The second file installs dependencies before copying source, so editing code reuses the npm layer and rebuilds in seconds.

One companion file earns its keep here: a `.dockerignore` listing `node_modules` and `.env` keeps local clutter and secrets out of the build context, so stray file changes stop invalidating the `COPY . .` layer.

```text
node_modules
.env
```

The other lever is the **multi-stage build**. Compile in a fat first stage carrying compilers, headers, and dev tooling, then copy the finished binary into a slim second stage like Alpine or distroless. The toolchain stays behind in the build stage, and images routinely drop from over a gigabyte to under 50MB.

The effect is easiest to demonstrate with a compiled language, and the same pattern applies to any build artifact:

```dockerfile
# stage 1: build, with the full toolchain present
FROM golang:1.24 AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o server .

# stage 2: ship, with the binary alone
FROM alpine:latest
COPY --from=builder /app/server /server
CMD ["/server"]
```

Only the second stage ships. The first is scaffolding that Docker throws away at the end of the build, which is the disposability idea from earlier wearing a builder's hat.

## Cheap to Replace

That's Docker end to end. An image you build once and run anywhere, a process that believes it owns a whole computer, a volume for the data that has to survive, and a build layout that keeps iterations fast. The philosophy underneath it all: containers are disposable. Delete one, start another from the same image, and it comes back identical in seconds. Once you trust that, a whole class of "works on my machine" problems simply stops existing.
